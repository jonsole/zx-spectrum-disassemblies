Alien 8 How the game is put together

Alien 8 is Knight Lore's engine carrying a new game, a year after Knight Lore and a year before Pentagram. Much is Knight Lore's, sometimes to the instruction: the main loop, the object record, the exits, the special objects that became the valves, the menu and the tune player. Much of the rest was reworked here -- the drawing, the depth sort's code, the collision code, the room builder, the control reader -- and those are the parts Pentagram took over nearly unchanged. What is Alien 8's alone is the game: the valves and the chambers, the clock, the remote-controlled robots, the turning robot, the scenes after a game. This page is the map of the whole: where things are, what runs when, and which parts come from where. Knight Lore's own page describes the engine as it was.

Memory

The tape's one block of code and data loads at $62FD and runs to the very top of memory; the loader enters it three bytes in, at $6300. Below it, over the system variables and the BASIC loader, the game keeps its variables and its object records, cleared before use. The block holds the level data and the sprites first, then the code, then -- in the part of it that is space, not game -- the screen buffer every picture is drawn into, the stack, and tables built at the start; the tape carries the mastering machine's leftovers there. The ROM is never called, since the game reads the keyboard and makes its sounds itself (its bytes are read only as noise), and interrupts are never enabled: there is no EI in the game, and the pause is a busy wait.

A game, a life, a room, a turn

AFTER_GAME is four loops, one inside another. A game: the variables and records cleared, the drawing tables built, five lives and 6000 light years, the menu (MENU), the start tune, the start records filled with one of four start rooms (NEW_GAME_START), the valves and extra lives dealt to their places (INIT_SPECIAL_OBJECTS), and every room's colour put back (RESET_ROOM_COLOURS). A life: NEW_LIFE copies the start records over the robot's two and takes a life, and with none left it is the game over (GAME_ENDED). A room: ENTER_ROOM files the valves of the room he left back in their places, builds the room into the object records (BUILD_ROOM), brings in what lies there from the places (FIND_SPECIAL_OBJS_HERE), puts him in the doorway he came by (ADJUST_PLYR_UVZ_FOR_ROOM_SIZE), and sets the drop latch in an even-numbered room. A turn: every one of the 56 records has its update routine run, and at the end of the turn (OBJECT_DONE) the turn is counted, what changed is listed and drawn in depth order (LIST_DRAWN, RENDER_DYNAMIC_OBJECTS), the turn is padded out, the clock runs (RUN_CLOCK), and the pause key is read.

Walking through a doorway jumps straight back to the room loop, dropping two return addresses from the stack by hand, after copying the robot into the start records ($C3B7), so a life starts where he last came in. A death is noticed at the end of a turn, when both of his records have emptied at the end of the sparkle, and goes back to the life loop. The game ends three ways -- the last life, the clock, the twenty-fourth chamber -- all at GAME_ENDED, which shows the summary and then sets GAME_OVER and runs the scene after the game in the same main loop, with no clock and no controls, until one of the scene's own routines goes back to the menu.

The update routines

An object record's first byte is its graphic number, and that number is both what is drawn (through the graphic table, GRAPHICS) and what runs: UPDATES has a word per graphic, the routine the main loop jumps to with IX on the record and the address of OBJECT_DONE on the stack. So an object animates, or changes its behaviour, by changing its own first byte: a valve becomes a seated valve four graphics on, the robot's legs become the in-between views as he turns and graphic 48, the sparkle, as he dies, and anything gone becomes graphic 1, which the drawing code empties. Most routines start by setting their own drawing nudge and end by moving through the collision code and, if anything moved, marking the object and what it overlaps to be drawn again (SET_WIPE_AND_DRAW_FLAGS). Scenery that never changes has NO_UPDATE, a RET.

Speed

Every turn visits all 56 records, empty or not, and then OBJECT_DONE waits six units of about 20,000 T-states less the drawing the turn has done, so a quiet room does not run faster than a moderately busy one; a room with six units of drawing or more runs as fast as it can. Even an empty room, with the robot standing still, does five units of drawing a turn, so the wait is rarely more than one unit. Watched in the emulator, standing still for 50 turns: 85 frames in an empty room, 95 in the start room $13. The clock counts turns, so it slows with the game.

Chance

SEED starts as the ROM's frame counter when the game is first run, has the last game's turn count added at every new game and one added every time round the menu's loop; it picks the start room, and with the refresh register the first kind of valve dealt. RANDOM is stirred with the refresh register after every object's turn and with the turn counter and a byte of the ROM at the end of every turn (OBJECT_DONE), so how long each update took feeds the next number. It decides where the extra lives go, when a thing drops from the ceiling or a leaper jumps, and which way a mouse turns.

Knight Lore's 40 records became 56 and the code that walks them followed: the list of what to draw holds all of them, which Pentagram, with 54, later got wrong. The fullest room fills 49 of the 52 room records. There is no day and night, no transformation and no cauldron; the clock is the time limit instead, and the chambers the goal.
