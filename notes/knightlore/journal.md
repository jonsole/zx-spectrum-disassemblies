# Journal

What was investigated, how, and what came of it. Newest last.

## Before these notes (2026-09-16)

The disassembly was built from tcdev's map (2017, as converted to SkoolKit by
Michael R. Cook, 2019): every byte in a block, labels from the map, a
round trip on every build. About thirty entries were described by hand -- the
start-up, the object walk, the menu's keys, the sprite format, the lookup
tables. The other 817 entries had only a placeholder title, 289 of the labels
were placeholders (`loc_B000`), and 20 of 8685 instructions had a comment.

## 2026-09-26

- **The build** was brought up to the other games': every routine lists its
  callers (`ListRefs=2`), `LD` operands link, and the routines list shows each
  name after its address. Labels are now renamed from
  `knightlore_annotations.ctl`, leaving the borrowed map file as it came.
- **Described in parallel.** The listing was split into eight ranges by
  subsystem and each given to an agent with one brief: describe every entry,
  replace the placeholder names, comment the instructions, and draft the
  notes. Three of them independently wrote comment drafts as instruction
  ranges with a script to count the bytes; that became `scripts/ctl_tools.py`.
  The notes here are their drafts, one subject a file.
- **Corrections to what had been written before**, each checked against the
  code before it was accepted:
  - The sprite header's width is bits 0-3, not `AND $7F`: bits 7 and 6 record
    whether the stored sprite is currently upside down or mirrored, since the
    game flips sprites in place. So spr_014's set bit 7, which had been an
    open question, just means the snapshot caught it upside down.
  - The sprite table at $7112 is a word per graphic number, not "type times
    eight plus a frame".
  - `read_port` does not select the half-row with its `OUT ($FD),A`; the
    `IN A,($FE)` after it puts A on the high address byte, which is what
    selects it.
  - The special-object table at $6FF2 is filled by `init_special_objects`,
    not `play_audio` ($B2CF, which the old annotation linked).
  - `game_loop` ($AFBA) is not "one frame": it is entered once per room.
  - The menu tune plays once and holds the menu up, not underneath it.
  - The room-size table's third byte is the floor height, $80 in all three.
- **Watched** in a private emulator: getting past the menu, the per-frame
  breakpoint ($AFBD, not `game_loop`), the room variable ($5C10), walking
  from room $8F to $8E, every bit of the input byte, and Caps Shift pausing.
  Two addresses in the remake's `driving.md` turned out to be off. See
  [`driving.md`](driving.md).
- **Pushing, watched.** Agents disagreed: one read the "moveable" block as
  unpushable, another read the collision code as pushing anything with +$07
  bit 2. Both were right about their own code: the collision code copies the
  push into the obstacle's velocity, and the handler decides. In room $8E, with
  the ghost removed (it killed the player in the first attempt, which spoiled
  that run), a table was pushed 28 units in 20 frames and the same table
  retyped as the moveable block did not move. See [`collision.md`](collision.md).
- **Level data out of the committed file.** The rooms, background pieces and
  charm places, described record by record, are generated by
  `scripts/knightlore_data.py` at every build rather than committed: 415 lines
  came out of the annotations. The generator was checked against the agent's
  decoding: all 128 rooms, 89 pieces and 32 places agree.
- **Warnings.** From 65 to none: plain addresses in comments became links or
  label references, the shift tables at $F200 got an entry of their own, and
  twelve instructions that load constants got `nowarn`.

- **Graphics and castle pages** for the site: sprites (drawn from their bytes,
  flips undone), objects (all 188 types with their handler and sprite),
  templates (the 29 block types), scenery (the 24 backgrounds), and room
  structure (the record format, a 16 by 16 map of the castle, and all 128
  rooms). The rooms, scenery and templates are drawn by the game's own code,
  run in SkoolKit's simulator by `scripts/knightlore_pages.py`. Getting there:
  the first pictures were black because each routine ran on a fresh simulator
  and `build_screen_objects` finds the room through IX, which `lose_life`
  leaves on the player; the frame had been stopped before the new-room copy;
  the panel is drawn into the room's own buffer, so the picture is read from
  the buffer just before the panel goes in; and the one-off rooms borrowed
  room 0, which brought its charm along.
- **Found on the way:** template 1, the fire standing still, and 17, the
  raised spikes, are used by no room -- as the remake's notes had said.
- **How a moving object is drawn**, end to end: a note and a site page that
  follow one object from its handler to the display, with frame 3 of room $01
  traced stage by stage in the simulator (3 rectangles, 14 objects redrawn).
  Reading the copy code settled an open question in `depth-order.md`:
  marking only the objects that overlap a mover's rectangle is enough, since
  only the rectangle is copied. The first trace hung on a different room -- the
  player's records had been emptied for the room pictures, and
  `next_frame_or_die` took that for a death.
- **The castle map** now looks like the classic ones (World of Spectrum's
  KnightLore_3): every room, drawn by the game, placed where the game's own
  projection puts it -- east is +X, down to the right, and north +Y, up to the
  right (`screen_east` adds 1 to the room number, `screen_north` 16) -- 128
  units apart, back to front, each on its floor diamond. Clickable on the
  page, and linked at full size.
- **`location_tbl` split into rooms.** Each room record is its own entry,
  `room8E` and so on, titled with its square, shape and colour -- generated
  with the rest of the level data, since the titles are the game's.
